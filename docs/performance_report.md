# Performance Report

## Abstract

This study evaluates an F1 Monte Carlo strategy engine as a reproducible ML Systems workload. The system progresses from a Python correctness reference through NumPy vectorization, CUDA, Triton, ML surrogate inference, real-time decisioning, distributed execution, scheduling, checkpoint recovery, and cost modeling.

The central question is: **How much can massively parallel GPU simulation and optimized ML inference accelerate real-time F1 strategy search?**

All values in this report are generated by benchmark execution or are explicitly labeled unavailable. No GPU performance is inferred when a CUDA device is absent.

## Problem

F1 strategy selection requires reasoning over many possible future race outcomes. Monte Carlo evaluation can be parallelized because simulations are independent. The systems challenge is to reduce decision latency while preserving statistical quality and making compute scalable and recoverable.

## System Architecture

```text
Race state -> candidate strategies -> ML surrogate / Monte Carlo
                                      |
                               strategy ranking
                                      |
                              GPU-aware scheduler
                           /      /       \
                        GPU 0  GPU 1 ... GPU N
                           \      |       /
                                aggregate
                                   |
                             best strategy
```

## Simulation Model

The Phase 1 simulator models tire compounds, degradation, fuel, weather, traffic, safety cars, pit stops, overtaking, stochastic noise, and DNF behavior. A fixed seed provides deterministic replay.

## GPU Architecture

The CUDA design maps independent race simulations to CUDA threads. Configuration is encoded once where possible, while per-simulation state and RNG streams remain independent. Phase 4 measured optimization effects under the CUDA simulator when real hardware was unavailable.

## CUDA Implementation

The repository contains both baseline and optimized CUDA paths. Optimizations include conditional stochastic work, reduced redundant ranking, and persistent configuration. Real-device measurements are only produced when a CUDA driver/device is available.

## Triton Implementation

The Triton path implements the selected lap-time hot operation using vectorized program instances rather than translating CUDA line-by-line. It is optional and skipped when Triton or a compatible GPU is unavailable.

## ML Surrogate

Phase 7 trains XGBoost and PyTorch models to approximate expensive Monte Carlo outcomes. Features include race state and strategy variables; targets include expected race time, finishing position, podium probability, and win probability.

## Inference Optimization

Phase 8 compares PyTorch precision modes and optional ONNX, TensorRT, and Triton inference paths. The available CPU environment measured PyTorch inference but did not contain the GPU deployment stack.

## Benchmark Methodology

- Fixed seeds and explicit workload sizes.
- Wall-clock runtime measured around complete execution paths.
- Throughput = simulations / runtime.
- Multi-worker scaling uses disjoint simulation partitions.
- Speedup = `T(1) / T(N)`.
- Scaling efficiency = `speedup / N`.
- Cold-start and warm decision latency are treated separately where applicable.
- GPU utilization, memory, power, and cloud cost are recorded only when measured or explicitly supplied by the user.
- Missing hardware is represented as `not_run` rather than estimated.

## Optimization Analysis

Phase 4's CUDA-simulator ablations remain part of the historical study: conditional stochastic work reduced simulated kernel time by approximately 39.9%, while persistent configuration reduced simulated host-to-device payload by approximately 30.2%. These are simulator measurements and are not equivalent to physical GPU timing.

Phase 8 measured CPU PyTorch precision behavior; GPU precision speedups remain unavailable in the current environment. The study therefore separates optimization mechanisms from measured hardware outcomes.

## Distributed Systems Analysis

A distributed workload does not automatically scale linearly. Each additional worker introduces scheduling, process startup, memory, transfer, and aggregation overhead. On actual GPUs, the same experimental framework should reveal PCIe/NVLink effects, kernel occupancy, launch overhead, synchronization, and load imbalance.

## Simulated AI Compute Cluster

Phase 12 adds priority-based GPU allocation, memory constraints, job states, batching metadata, completion, failure, and retry. The scheduler is workload-agnostic so simulation and inference jobs can share resources.

## Fault Tolerance

Phase 13 stores completed simulation ranges and derives deterministic per-simulation seeds. A failed worker only requires the missing range to be retried. The benchmark confirms checkpoint save/load and missing-range detection.

## Cost and Energy

Phase 14 intentionally does not use arbitrary cloud prices or power numbers. Cost results are generated only when a real GPU hourly price is supplied and a measured CUDA runtime exists. This prevents a cost chart from becoming a disguised assumption.

## Limitations

- No NVIDIA GPU/driver is available in the benchmark environment.
- No physical GPU utilization or power measurement is available.
- Triton, TensorRT, and ONNX Runtime are not available in the environment used for the release validation.
- CPU fallback scaling includes multiprocessing overhead and should not be interpreted as GPU scaling.
- The scheduler is a research/reference scheduler, not a production cluster manager.
- Cloud cost depends on provider, region, reservation model, and GPU type.

## Future Work

- Run the same fixed experiment on 1, 2, 4, and 8 physical GPUs.
- Add NCCL-based result aggregation.
- Measure PCIe/NVLink transfer and synchronization overhead.
- Integrate NVML telemetry for utilization, memory, and power.
- Add persistent distributed checkpoints and worker heartbeats.
- Add real cloud pricing adapters.

## Conclusion

The project now represents a complete experimental stack rather than a single simulator: simulation, GPU kernels, ML inference, distributed execution, scheduling, reliability, and cost modeling. The most important methodological result is that the system distinguishes measured performance from unavailable hardware results. The next scientifically useful experiment is to run the existing reproducibility scripts on a multi-GPU host without changing the workload or seeds.
